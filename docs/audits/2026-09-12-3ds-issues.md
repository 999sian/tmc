## 1. P1 — EU logical sprite indices are used as native ROM indices

**Source:** `include/definitions.h:447`, `src/projectileUtils.c:53–56`, and projectile definitions in `src/projectile.c:58`, `:66`, and `:153`.

The EU ROM omits `SPRITE_OBJECTB4_1`. A multi-region executable is compiled with the USA sprite enumeration, but `ProjectileInit` assigns the compiled sprite index directly to the entity. Later animation and geometry reads use the active EU ROM table.

| Object | Current compiled index | Correct EU index | Incorrect EU table selected |
| --- | ---: | ---: | --- |
| Cannonball | 291 | 290 | Vaati eye laser |
| First-form Vaati eye laser | 292 | 291 | Dark magic |
| First-form Vaati dark-magic shield | 293 | 292 | Slime |
| Second-form Vaati eye | 297 | 296 | Body-effect geometry |

### Reproduction

The #33 attachment identifies an EU ROM, area `0x88`, room `0x34`, player-relative position `(122,174)`, layer `2`, and collision source `CANNONBALL_PROJECTILE` (`0x1B`). At frame 780 the baseline renders fragments. A debugger intervention changing only `spriteIndex` from 291 to 290 at `CannonballProjectile_Init` restores round cannonballs; eight instances were observed.

For #35, invoking production `InitializeAnimation` on an unused entity with the EU ROM gives:

```text
sprite 292, animation 2: animPtr=NULL, frame=0
sprite 291, animation 2: valid animPtr, frame=9
```

The correct laser table has seven animations; the incorrectly selected dark-magic table has two followed by NULL and adjacent data. Collision is enabled independently of animation success (`src/projectileUtils.c:53` and `src/projectile/v1EyeLaser.c:41`). Thus failed visual initialization does not remove the attack's collision.

**Intended behavior:** after the second phase transition, Vaati's balls acquire dark-magic shields and initially resist normal attacks. The special collision sound is explicitly requested by `src/projectile/v1DarkMagicProjectile.c:84`; the shield setup is in `src/enemy/vaatiBall.c:240`. These facts alone are not bugs. The existing PC shield-parent layout and stale-latch fixes are already present; no additional ordinary orb-deletion defect was established.

**Upstream status:** [3b05a85e](https://github.com/EstebanPdN/zelda-tmc-3ds/commit/3b05a85eeba2f9fd053ec7ceb875040d3d25db9b) adds source-boundary remapping for Vaati projectiles and others; [3541457f66](https://github.com/EstebanPdN/zelda-tmc-3ds/commit/3541457f66) separately fixes second-form eyes. E16's `src/projectileUtils.c:66–69` still excludes `CANNONBALL_PROJECTILE`.

**Recommended fix:** port the logical-to-native mapping at audited C-definition assignment sites, including cannonballs and second-form eyes. Do not remap every sprite getter: ROM-derived and existing EU-specific definitions already contain native indices and would be remapped twice. Add regional controls for cannonball, laser animation 2, dark magic, and second-form eye geometry.

**Evidence:** `/tmp/tmc-audit-33/FINDINGS.md`, `correct.gdb`, `correct.log`, `pc-eu-baseline360.png`, `pc-eu-corrected.png`; `/tmp/tmc-audit-35/laser.gdb`, `laser-runtime.log`, `rom-sprite-evidence.json`.

## 2. P1 — Additional room-entity lists still load from USA addresses on EU/JP

**Source:** `port/data_stubs_autogen.c:643–712`; consumers include `src/roomInit.c:2424` and unbounded traversal in `src/room.c:59`.

All 26 additional-list entries use fixed USA offsets. Comparing those reads against the three valid ROMs found no `0xFF` record terminator inside the copied extent for **22 EU lists and 23 JP lists**; all 26 USA copies contain their terminator. This is a data-initialization defect, not merely a possible offset discrepancy.

GDB inspection after actual `Port_LoadRom` confirmed:

| Runtime list | USA record kinds | EU record kinds | JP record kinds |
| --- | --- | --- | --- |
| Deepwood boss rewards, 48 bytes | `06 06 FF` | `02 00 00` | `FF FF 00` |
| Melari main list, 96 bytes | `07 07 07 06 06 FF` | `DC 00 88 38 38 68` | `15 00 00 00 00 00` |

JP's boss reward list starts with the terminator, so the consumer immediately returns without spawning the two reward entities. EU's copy and many other regional lists lack a terminator within their intended data; `LoadRoomEntityList` can walk beyond that data and interpret unrelated memory as entity records. Natural playthrough crashes were not reproduced during this audit.

**Upstream status:** E16 has separate USA/EU offsets for these lists. It still falls back to USA offsets for other regions; that is not a JP fix to import unchanged.

**Recommended fix:** resolve every list from the active region, validate the destination capacity and terminator, and retain independently checked JP mappings. Cover boss rewards, Melari, the library, and inn/oracle lists with runtime initialization tests. Do not attribute this automatically to upstream #31: the current upstream EU path already differs.

**Evidence:** `/tmp/tmc-audit-extra/entity-lists.json`, `inspect.gdb`, and `{USA,EU,JP}/inspect.log`.

## 3. P2 — Moving lily-pad rail pointers are never initialized for EU/JP

**Source:** `port/port_rom.c:1352`, `src/object/lilypadSmall.c:58–63`, `src/objectUtils.c:396`.

The initializer is explicitly USA-only. After loading each ROM in a fresh production process, `gLilypadRails[0..2]` were valid for USA and all NULL for EU and JP. Small lily pads using `type2 >= 0x80` select these pointers; `UpdateRailMovement` does nothing with NULL, leaving their movement uninitialized. Kinstone-created rail paths also use this table.

The three-pointer table was independently located in retail ROMs by consistent pointer relocation and matching first rail commands:

| Region | Table ROM offset |
| --- | ---: |
| USA | `0x0FED98` |
| EU | `0x0FE2DC` |
| JP | `0x0FEA48` |

**Upstream status:** E16 initializes this table through `RomOffsets` for USA/EU; its JP field remains zero.

**Recommended fix:** populate all three regional addresses, resolve the pointers at ROM load, and verify an affected moving platform and a kinstone-created rail. The NULL runtime pointers and no-op consumer are confirmed; a complete platform traversal was not performed.

**Evidence:** `/tmp/tmc-audit-extra/{USA,EU,JP}/inspect.log`.

## 4. P2 — Death-effect allocation failure causes two NULL dereferences

**Source:** `src/enemyUtils.c:246`, `:256`, and `:271`.

`CreateObject(DEATH_FX, ...)` may fail when the entity pool is exhausted. The initial setup correctly checks its result, but two later branches dereference it unconditionally:

- `EM_FLAG_NO_DEATH_FX`: `deathFx2->unk6c |= 8`.
- Gust-related contact type `0x13`: `deathFx2->base.parent = NULL`.

A reduced UBSan harness containing the production function body and an allocator forced to return NULL reports null-member access for both paths. This establishes the function-level failure; natural gameplay pool exhaustion was not reproduced. The boss-specific branch has its own NULL check, so this is **not evidence of #31's cause**.

**Recommended fix:** guard the two writes while preserving enemy deletion, and test both failure paths plus successful allocation.

**Evidence:** `/tmp/tmc-audit-31/deathfx_oom.c`; running the compiled harness with no argument and with `gust` fails under UBSan. The separate invalid-state experiment in `oom/run2.log` is excluded from the evidence.

## #31: what remains unresolved

The current upstream and PC `chuchuBoss.c` files are identical. PC forced-death tests with correction disabled/enabled both completed normally through the post-death capture. Color correction is applied in different places on the two platforms: PC framebuffer postprocessing (`port/port_ppu.cpp:631–655`) versus 3DS palette conversion. The report's Old 3DS dependency and color-correction observation therefore do not justify a PC code change without a hardware crash trace or a stronger reproduction.

E15's `f9984989e3` texture fix concerns the updater UI only and is not established as a fix for this boss crash.

Evidence: `/tmp/tmc-audit-31/kill.gdb`, `{off,on}/run3.log`, and `{off,on}/roomcap.png`.

## Follow-up audit: additional confirmed findings

The second pass used isolated production-runtime probes and ROM comparisons. It made no production changes. Injected states establish failure paths, not their frequency during normal play.

### 5. P1 — EU extended tile collision uses the wrong shape pointers

**Source:** `port/port_linked_stubs.c:578`, `src/playerUtils.c:3012`.

Both tile collision lookup and player edge adjustment resolve pointers from the compiled USA `gUnk_0800823C` table against the active ROM. The native EU table is at `0x82D4`, instead of USA/JP `0x823C`; all 40 EU shape pointers are relocated by `0x98`.

A production `sub_080086D8` call with collision type `0x10`, normal collision parameters, and tile-local pixel `(9,0)` returned blocked (`1`). The correct EU mask returns passable (`0`). This proves an incorrect collision result; specific naturally encountered blocked routes were not mapped. JP's pointer table matches USA. This is separate from the enemy collision matrix fixed for #193.

**Recommended fix:** resolve shape data through the active region for both consumers, following upstream `Port_GetCollisionShapeData`.

**Evidence:** `/tmp/tmc-audit-extra-collision/expected.json`, `check.gdb`, and `runtime.log`.

### 6. P1 — EU tile properties are read from the USA address

**Source:** `port/port_linked_stubs.c:1845`, `:1870`, and `:1879`.

The property lookups hardcode ROM offset `0x360`; EU requires `0x3A8`. In a production probe, tile type zero returned `0x57CC` instead of the correct zero. Comparing 1,394 entries found 660 differences. Consumers include player layer/priority checks, lantern queries, and projectile tile flags. These incorrect properties are confirmed; this probe does not attribute a particular reported gameplay symptom to them.

**Recommended fix:** centralize regional tile-property resolution, including the lantern's other-layer fallback, following upstream `Port_GetTileTypeProperty`.

**Evidence:** `/tmp/tmc-audit-extra-collision/runtime.log` and `check.gdb`.

### 7. P2 — EU HUD emits stray geometry and loses item tile data

**Source:** `src/ui.c:117`, `:658`, `:950`; `port/port_rom.c:1434`.

This extends finding 1 to another initialization path. HUD definitions use USA button sprite 505 and item/text/hearts/Ezlo sprite 322; EU requires 504 and 321. The HUD sprite-table seed also uses 322. EU sprite 322 has NULL frame/tile pointers, so the tile loader suppresses item art.

Matched frame-600 room captures show that correcting only HUD definitions and the table seed removes the white statue-like fragments along the top of the screen. Cannonballs remain wrong, and the actual statues already use the correct native index 289. Thus the apparent duplicated statues are HUD output, not an additional statue defect.

**Recommended fix:** map the HUD definitions and seed consistently alongside the projectile fix. Upstream E16 covers this HUD path.

**Evidence:** `/tmp/tmc-audit-extra-sprites/FINDINGS.md`, `probe.png`, `ui-corrected.png`, `probe.gdb`, and `fix-ui.gdb`.

### 8. P1 — EU wall fusions read unrelated records

**Source:** `src/common.c:1591–1599`, `port/data_const_stubs.c:195`.

The wall-fusion resolver unpacks compiled USA pointers and resolves them against the EU ROM. The correct EU pointer table is at `0x1E74`. For wall fuser `0x68`, the current pointer `0x080022B3` produces a required story progress of 56; the correct pointer `0x0800235B` produces zero. Normal story progress reaches at most 9 (`src/gameUtils.c:939`), so the current requirement rejects this fusion. All five wall records `0x66–0x6A` differ; four have impossible progress requirements.

**Recommended fix:** use the active region's fusion records, with bounds checks, following upstream `Port_GetFuserFusionData`. Review the distinct native entity-to-fuser lookup as well. This establishes the record and rejection path, without a full wall-interaction playthrough.

**Evidence:** `/tmp/tmc-audit-extra-story/runtime.log`, `probe.gdb`, and `wall-rom.json`.

### 9. P1 — Large chests can commit collection without granting a reward

**Source:** `src/object/chestSpawner.c:219`, `:236`; `src/playerItemUtils.c:24`.

During the opening delay, the chest marks its completion flag before reward creation. Later it calls the void `CreateItemEntity` wrapper, which discards allocation failure. A production probe changed `flag=0, action=4, subtimer=2` to `flag=1, action=4, subtimer=1`, before reward code ran. With seven auxiliary slots occupied, the reward allocator returned failure. Together these establish a region-independent path to a collected chest with no reward. Capacity exhaustion was injected; its natural frequency was not measured.

**Recommended fix:** use `CreateItemEntityWithFlag`, defer ordinary completion to `LinkHoldingItem`, and restore interaction on allocation failure, as upstream does. Preserve the separate rupee-fountain behavior.

**Evidence:** `/tmp/tmc-audit-extra-story/runtime.log` and `probe.gdb`.

### Candidates excluded from the confirmed list

- Upstream bomb, wall-cursor, and Goron bottle repairs include migrations for previously damaged EU saves. Their absence does not establish a fresh-game PC defect. The current initial bomb-bag grant correctly grants bombs; no link between the chest allocation defect and the reported Goron save was established.
- The extra-frame-offset blobs differ between regions, but decoding sprites 0–327, frames 0–15 found identical attachment coordinates due to compensating relative offsets. Byte differences alone do not prove broken multipart NPC attachments.
